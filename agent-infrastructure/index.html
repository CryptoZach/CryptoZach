Agent Infrastructure

Run many AI agents on one codebase while keeping the work coordinated, attributable, and reproducible.

We built an operating layer that isolates concurrent work, records which agent and session produced each shared result and what it relied on, keeps shared references valid, and measures whether safeguards change behavior. It has run on our own fleet since March 2026.

The evidence is below: dated measurements from more than 67,000 commits, the controls that held, the warnings that repeated, and the failures that changed the design.

Why this layer matters

When many agents share a codebase, small errors stop being local. They become shared state that later agents can trust, repeat, and extend. Three requirements keep those errors from compounding.

  • Concurrent work needs isolation. Without separate workspaces and durable ownership, two agents can change the same files and one can quietly erase the other's work.
  • Shared results need identity and provenance. Later sessions need to know which agent produced a result, what evidence and prior state it used, and whether its references resolve to real records.
  • Safeguards need outcome measurement. A warning count shows that a message appeared, not that behavior changed. A gate count shows that it fired, not that it held or was bypassed.

Only outcome measurement turns an assumed safeguard into a verified control.

The next section names the three jobs. Shared memory comes immediately after, because every reused result must trace to a verified record. Scale and the measurement sections follow, and the closing section states the scope and validation boundaries of a single-fleet study.

The operating layer

The layer has three jobs. Each replaces something an agent would otherwise have to remember with durable state, a machine check, or a measured outcome.

Keep concurrent work isolated and recoverable

Each session works in its own isolated working copy and staging area. Ownership is stored as a time-limited lease. If a session exits, the lease expires and its work returns to the queue instead of remaining silently claimed.

See why process-based ownership failed

Preserve identity, provenance, and valid references

Shared work records which agent and session produced it, what evidence and prior state it used, and the exact commit that wrote it into the durable record, so any result can be traced to the change that saved it. Findings, decisions, and open questions must resolve to existing records; missing references are surfaced instead of invented.

See how an invented reference spread

Measure safeguards by outcomes

Warnings are graded by whether they return after first appearing. Hard gates are graded by how often they stop an action or are bypassed. That separates controls that teach, controls that enforce, and controls that only appear active.

Shared memory needs identity and provenance

The operating layer's second job is to keep a shared result from being trusted before it can be traced. Memory capacity and retrieval matter only after that. Before one agent reuses another's result, it needs four answers: does the referenced fact exist, which agent and session produced the result, what evidence and prior state did it use, and which commit wrote it into the durable record?

The failure that forced this design was confabulation rather than forgetting: an agent confidently cited a finding with no backing record. The next session accepted the citation as real and built more work on top of it. In shared memory, one invented identifier can become load-bearing within a few sessions.

  1. Require valid references when work is saved

    Every reference to a finding, decision, or open question must resolve to an existing record; unresolved references remain empty and flag for human review.

  2. Preserve attribution with the result

    Shared work records the producing agent and session, the evidence and prior state it relied on, and the committed change that placed it in the durable record.

  3. Verify that instructions reached the reader

    Provenance requires confirming that the instruction reached the reader. Startup procedure files have a hard size limit; content beyond that limit can be truncated, so loading and size checks verify that the full record arrived.

Shared memory is trustworthy only when records are valid, attributable, and known to have reached the reader.

Who still holds the work after the producing session exits is covered under coordination.

Measure whether safeguards change behavior

A warning can fire thousands of times and still have no effect. To separate activity from effectiveness, we track what happens after a workspace first sees each warning. A workspace is one agent's isolated checkout of the shared codebase.

The core metric is repeat rate (called saturation inside the instrument): the share of workspaces where the same warning appears again after its first appearance. A high repeat rate shows the behavior requires an enforcing gate; a lower rate is consistent with teaching while remaining an observational association.

The largest result

The warning for treating a failed command as successful generated 13,975 events, more than half of all warnings, and returned in 84% of workspaces. A trigger dashboard would make it look heavily used; outcome data showed that stopping the mistake required an armed gate.

The result persisted when the observation window was held constant. Over equal windows of 595.6 hours (24.8 days) either side of 2026-08-04, re-measured on 2026-09-21, the failed-command warning moved from 81% (2,683 firings) to 87% (7,767 firings), while the unscoped-absence warning moved from 64% (606 firings) to 48% (1,078 firings). Stating the exact span makes the comparison reproducible: the instrument bounds both windows to the shorter side, so running the command later compares longer spans. Classes with sparse observations on either side remain ungraded so only powered comparisons receive a verdict.

Grade a safeguard by what agents do after it fires rather than by how often it appears.

From advice to enforcement

Rules operate at two levels based on how precisely the system can distinguish an unsafe action from valid work.

Teaching control

Explains the safer action and relies on the agent following it. Examples include a session-start rule, a memory entry, or a warning. It remains guidance until outcome data shows that behavior changed.

Enforcing control

Changes what the agent can do at the moment of action. A gate can refuse a commit or command, while a helper can return the safe form directly. It operates independently of agent recall and requires a precise boundary between unsafe and valid actions.

Enforcement requires delivery at the point of action. A documented, loaded, or triggered rule becomes an enforcing control only when its delivery path intercepts the action and refuses or removes the unsafe choice.

Two design rules follow:

  • Escalate only when the harm and the target are clear. Arming a hard gate requires both a high-repeat failure mode and an unambiguous signature for the prohibited action.
  • Measure false positives and overrides before arming. A gate that blocks valid work will train agents to bypass it or will be disabled entirely.

The strongest control replaces the unsafe path with a safe actuator; where an actuator is unavailable, a narrow hard gate refuses the command and logs every override.

About 11% of warnings reached a hard gate. A gate is safe to arm only when the wrong action is unambiguous. Destroying a stash or force-deleting a branch can be recognized from the command. Piping one command into another is usually valid, so most failed-command warnings still remain advisory.

The failed-command class now has a deny mode that fired 2,080 times against 13,975 events (about 15%), with 9 documented overrides. The other 11,886 events in the class stayed advisory. The gate reaches more of the class than it did in August, while the broader piped-command cases remain advisory.

A gate is effective when it intercepts the target behavior and holds with a low override rate.

When a gate measures machine load instead of risk

One launch gate blocks new work when it cannot read the current ownership state. A week after arming, that read failed in 22% of attempts, causing dozens of blocked launches each day. Agents used the override in 29% of those cases.

System load drove the timeouts: the ownership read slowed when the machine was busy, converting CPU contention into blocked launches. Because a retry often succeeded, the gate trained agents to retry instead of investigate.

With no change to the gate, the same measurement later fell to 1.8%: ten failed reads across 543 attempts, five blocked launches, and no overrides. The drop reflected lower machine load rather than a change in the gate itself (measured during the August 2026 episode).

Measure what drives a gate's trigger rate, then count how often it fires.

Coordination must survive the agent

Hard gates intercept single commands; durable coordination governs who holds a task across session exits. In the early system, task ownership relied on messages sent to a running process. When the receiving agent exited, its task remained marked as claimed with no active worker, leaving the rest of the fleet unable to see or recover the work.

Now every claim is stored in committed state as a lease: a time-limited ownership record checked whenever the queue is read. If the lease expires or its holder is gone, the work returns to the available pool instead of remaining silently owned.

Who is working on it now?

This is a live-state question. An absent process can show that the current holder is gone.

Who remains responsible?

This is a durable-state question. A stopped process does not erase the work item's history, responsibility, or next action.

Leases protect ownership state; isolated workspaces protect the files. Every session receives its own working tree and staging index, so one agent cannot silently alter another agent's pending commit.

Coordination state should outlive the process that created it.

Ownerless work needs a queue that escalates

A finding mentioned in a session can disappear when that session ends. A finding written only in a commit message is durable but has no process that will return to it. Sending it to another live agent creates the same dependency on a process that can exit.

The system therefore files ownerless findings in a committed queue. Each entry appears in every session's startup summary, escalates as it ages, and can be claimed only through a time-limited lease. It leaves the queue only when it closes with evidence.

Every entry must say how closure can be verified. Managing a continuous arrival stream with a rate target

The queue owner was originally told to assign every unclaimed entry. At 95 arrivals a day, that would require roughly 95 new assignments every day. The workable duty is a rate target: close at least as many entries as arrive.

The obsolete absolute duty remained in a startup file after the rate target replaced it. Two consecutive role holders then failed in the same way because both loaded the same impossible instruction. Replacing the person left the startup instruction unchanged. The same split appears when a startup file loads only part of its instructions, and when a committed rule differs from the copy that executes.

When a rule is written in two places, the copy that reaches readers governs, whichever copy is current.

Separating a bounded scan's budget from the full backlog

The queue listing checks whether entries are already resolved and stops at a fixed time budget, labeling remaining entries as unmeasured. A complete run on 2026-08-08 found 22 entries that were already resolved but still aging, escalating, and inflating the visible backlog.

The label was honest, and sessions still treated the visible total as the full backlog. When an instrument stops early, readers need both the measured result and the size of the unmeasured remainder.

A passing check can still be wrong

The queue scan above carried an honest label for an incomplete pass. A false-green result is a sharper risk: an assertion can pass without proving that the check read fresh state, reached the intended target, or could distinguish a valid state from a broken one.

Right answer, invalid check

A verifier reported that an external record was live. The record was live, but the network request had timed out and the assertion matched bytes left behind by the previous request. The answer was correct by accident.

The correction was to clear state before every request, treat a failed request as could not determine, and test a deliberately false identifier to prove that the verifier could reject it.

A check is trustworthy only after it has been observed to reject a known fault.

Different causes can share one symptom

A burst rate limit and an exhausted usage budget can produce the same error while requiring opposite responses. A defect in code around a model can look like a model failure. The check must isolate the underlying cause rather than matching the shared symptom. When model output appears wrong, the verifier is tested before the model is blamed.

Reading the shared branch alongside the local checkout

Each session runs in a separate, often partial checkout where an absent local file indicates only local checkout state. The shared branch may already contain the file while the local copy sits hours behind. Repository-state checks therefore read the shared reference or staged index and return three answers: present, absent, or could not determine.

Verifying that the committed rule is the copy executing live

A rule can be committed to the shared branch while an older copy continues to execute. This happened when commit hooks loaded their code from a different checkout than the one carrying the new rule. The system now compares the bytes being committed with the bytes the hook will actually run.

A rule is delivered only when you can name how it reaches agents and show it being read or enforced.

Context is a finite operating budget

Identity and provenance make a record trustworthy. The context window still limits how much of it an agent can hold at once. Loading every procedure, source, and prior result at startup can crowd out the evidence needed for the current task. Four rules keep that budget usable.

  1. Load procedures only when they are relevant

    The system has 78 program skills, but none loads automatically at session start. Each skill exposes a short description first; its full instructions load only when the task requires them.

  2. Write large results to durable storage

    Results above a fixed size go to disk, while the agent receives a short digest and a path. A cost estimator checks large reads before they consume the context window.

  3. Measure remaining context during the task

    The agent can query occupancy and headroom, meaning the context still available. Explicit thresholds say when to continue, checkpoint the work, or hand it to a fresh session.

  4. Rotate memory instead of weakening retrieval

    The startup memory index is capped at 25,000 UTF-16 units or 200 lines. The 24.4 KB figure on the previous revision was 25,000 divided by 1,024. Re-measured on 2026-09-21, the live index held 21,605 units and 160 lines, with 128 entry pointers and every linked file present. Shortening the text that says when an entry applies would make retrieval less reliable, and trimming the non-pointer lines reclaims little, so entry count remains the lever. Complete entries rotate into a searchable archive. An earlier reading of 105 pointers in 19.7 KB, against a 1,466-entry corpus, was not reproduced with that corpus definition on this pass.

Context management must preserve retrieval accuracy while bounding token footprint.

Eleven failures, one pattern: the signal looked healthy

Each failure here was quiet: nothing crashed and no error appeared. A warning fired, a claim was held, a check passed, a rule was committed, and each of those signals looked like a control doing its job. In every row, a second measurement showed the signal meant something else.

The most dangerous control is one that fails silently toward the reassuring answer.

Three practices transfer beyond this system:

  • Test a known false case. A check proves it can distinguish success from failure only after rejecting a known fault.
  • Keep “could not determine” as its own result. Separating uncertainty from absence keeps an uncompleted check from reporting a false clean result.
  • Verify delivery and execution separately. Show both how the control reaches agents and which version is actually running.

Several of the eleven failures were first spotted when a human reader noticed that an output conflicted with reality. The instrument turns each discovery into a permanent check so catching a recurrence relies on automation rather than luck.

One control-layer thesis: from programmable money to AI agent fleets

Why did a tokenization and market-structure research program build an operating layer for AI agent fleets? Because both systems fail at the exact same seam when an institution mistakes a surface claim for an enforced control. In programmable money, a token's label states its intended peg while the control layer governs how reserves, redemptions, and settlement behave under stress (Routing the Dollar, Minimum Viable Equivalence Pack, The Control Layer War). In multi-agent software and autonomous commerce, a prompt rule or advisory warning is the equivalent of a token label: it states intended behavior, whereas an armed gate enforces execution.

Scope and validation boundaries

The operating layer runs daily in production on our fleet; cross-organization reliability requires second-environment measurement. Five boundaries define the scope of these results.

  • Current access. The layer runs every day for one research program, and a product is being built from it. External access currently runs through design partnerships while public release and pricing remain in development.The available ways to engage are below →
  • External validation. Every measurement comes from one operator's fleet. Extending these findings to outside teams requires measuring transfer in a second operating environment.
  • Technical scope. The layer coordinates agents, preserves attribution and shared-state integrity, and evaluates controls around existing foundation models.
  • Security scope. Isolated sessions protect cooperating agents from corrupting one another's work and complement dedicated sandboxes for untrusted or hostile code.
  • Generalization. The results describe this system's controls under its observed workload. Observation periods and counting rules remain attached so readers can judge how far each result should travel.

What exists today. The layer has run on our fleet since March 2026 and is measured continuously. Its architecture is covered by 42 USPTO applications across 32 families. The surrounding research program includes nine papers on SSRN, one peer-reviewed publication in Frontiers in Blockchain, and 25 federal regulatory comment letters.
