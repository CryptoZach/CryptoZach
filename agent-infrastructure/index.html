Agent Infrastructure

AI agent fleets need an operating layer that can prove its controls work.

We are building that layer: durable coordination, identity and provenance for shared work, memory with referential integrity, and controls graded by what agents do next. It has run our own fleet since March 2026. This page shows what held, what failed, and what changed.

The differentiator is measurement. A warning firing is not evidence it worked, and a rule landing is not evidence it ran. We measure behavior, refusals, overrides, and delivery paths so weak controls can be redesigned before they become trusted infrastructure.

Why this layer matters

This page is for anyone deciding whether agent infrastructure matters, without needing to understand every mechanism. Once many agents share a codebase, correctness depends on three capabilities that ordinary task runners do not provide.

  • Concurrency needs isolation. Two agents can change the same state under a rare interleaving, and one can quietly erase the other's work.
  • Shared memory needs integrity. One invented reference can be accepted by the next session and become load-bearing within days.
  • Controls need outcome data. Trigger counts show that a warning fired. They do not show that the warning changed behavior or that the enforcing code ran.

A control you have not measured is a control you are only assuming you have.

The operating layer is the part of a fleet that keeps shared work correct. The rest of this page shows the system, the measurements that changed its design, and the boundaries on what those measurements establish.

What we are building

Three capabilities, in the order a fleet breaks without them. Each is linked to the failure that forced its design.

Coordination that survives an exit

Ownership is durable state with an expiry, not a pointer to a running process. When a session exits, its work returns to the pool, and ownerless work enters a queue that escalates on its own. See the failure that forced it.

A shared record with identity and provenance

Shared work retains attribution: which agent and session produced it, what evidence and prior state it relied on, and which committed change made it durable. Findings, decisions, and open questions must also resolve to existing records; missing references are surfaced instead of invented. See the failure that forced it.

Controls that are measured

Each safeguard is graded by behavior after exposure, plus refusal and override rates where a gate is armed. That separates teaching, enforcement, and decoration. See the measurement method.

The largest current boundary is explicit: every number on this page comes from one operator's fleet. See the full scope and limits.

Which controls change behavior?

The first instrument answers one question about every advisory: after a workspace sees the warning, does the same warning keep returning?

The metric is saturation: the share of workspaces where the same warning fires again after its first appearance. A high repeat rate is evidence that teaching alone is insufficient. It is not proof that every warning was read or that no behavior changed.

What the loudest advisory showed

Pipe-exit misread is more than half of all warnings, and it repeated in 85% of workspaces that had already seen it. That is a fact about teaching-level advice, which is why enforcing controls exist. It is not a score of the operating layer.

This finding changed the architecture. A trigger-count dashboard would have shown a busy control. Saturation showed that advice alone was insufficient, which led us to separate teaching-level guidance from enforcing controls.

Nineteen days of further observation did not improve the result. On a fixed-length comparison window, pipe-exit misread moved from 81% to 87% while unscoped negative claim moved from 64% to 55%. The data records the movement without assigning a cause it cannot establish. Six other classes return no verdict because they are under-sampled.

Measure whether controls change behavior, then redesign the ones that do not.

Enforcement levels

The saturation measurement forced a distinction that now governs every new rule. Call each level a rung: how strongly the system actually enforces the rule, from advice the agent can ignore up to a hard block that removes the wrong action.

Teaching level

Works only if the agent recalls the rule while acting: prose in a session-start file, a memory entry, an advisory warning. Easy to ship; easy to ignore under time pressure.

Enforcing level

Does not depend on recall: a gate that refuses the commit, a hook that denies the call, or a helper that returns the correct command form so the wrong one is never expressible.

The rule that follows: a control shipped only as teaching-level advice is unenforced, and the honest thing is to say so rather than count it as delivered. Two corollaries, both learned the expensive way:

  • Promote on evidence of harm, never on elapsed time. A rule that has sat quietly for a month has not earned a stronger enforcement level; it has only failed to be noticed.
  • Measure the new control's precision before shipping it. Otherwise you rebuild the same cry-wolf problem one level up, with more authority behind it.

The strongest form is the one that removes the choice. A checkout that refuses commits and whose refusal message names the correct command is categorically different from a warning that explains the same thing, because the first cannot be forgotten under time pressure.

What enforcement changed, and where it did not

An escape hatch remains necessary because an incorrect gate with no recovery path is likely to be disabled entirely.

What can be armed is decided by ambiguity, not by will. Those 287 events are 2% of the 13,140 warnings in the same window. Look at what is on the list: destroying a stash, force-deleting a branch, garbage-collecting the object store. In every one the wrong action is unmistakable from the command alone. The loudest class in the system is missing from the top of that list precisely because piping one command into another is usually correct, and only a subset is a misread. You cannot promote a control to the enforcing level faster than you can say exactly which action is wrong, and for the noisiest classes that is the part nobody has.

A refuse scoped narrowly enough to be safe can be scoped narrowly enough to be pointless. The narrow pipe-exit refuse has fired six times in the fifteen days since arming, against 8,352 advisories in the same class over the window. It reaches under a tenth of one percent of the population it was built for. Five of those six refusals were overridden inside one second by the same agent re-issuing the identical command with the escape prefix, and four of the five were one command in one workspace, hit and stepped over four times across fourteen hours. So the refuse is doing one thing well and one thing badly: it is not crying wolf, and it is also not stopping anyone.

An enforcing control is proven by hold and override rates, not by the word gate.

When gate cost tracks load, not risk

One more gate is worth the space, because it inverts the usual question. It refuses to start new work when it cannot establish what other sessions have already claimed, and it was armed in early August, the day its trigger first fired against a zero baseline. A week later it was firing on 22% of its reads (the trigger rate: the share of attempts where it could not establish that state), refusing dozens of launches a day, and operators were routing around 29% of them, which by the rule above is a gate failing.

The mechanism was not contention. The gate fires when the read of shared state fails to complete, that read times out more often as the machine saturates, and so an armed refusal was quietly converting machine load into refusals to work. A refusal that clears on a plain retry teaches operators to retry rather than to check, which is the worst thing a gate can teach.

Measured again for this revision, with nothing about the gate changed: the trigger rate is 1.8%, ten of 543 reads over twenty-four hours, producing five refusals and no overrides. The control did not get better. The load fell.

The cost of a control is not a property of the control. Measure it more than once, and find out which of its inputs is the one actually moving.

Invented facts before forgotten ones

The same shape appears in the memory layer, and it is worth its own section because the usual framing hides it. Memory systems for agents are discussed as a capacity problem: how much they can store, and how to retrieve it. In practice the failure that nearly broke this one was not forgetting.

It was an agent writing a confident citation to a finding that had never been established. The next session then treated that citation as real, and built more work on top of it. Researchers call this confabulation (a made-up fact stated as if it were true). The shared record does not degrade gracefully under that. A single invented ID can become load-bearing within a few sessions.

The fix was not a better search tool. It was a commit-time rule: no agent may invent an ID for a finding, a decision, or an open question. If the ID is not already in the corpus, the slot must be left empty and flagged for a human. In other words, every cross-reference has to point at something that already exists.

Shared memory needs valid cross-references more than it needs better recall.

A second, quieter failure in the same family: instructions that are supposed to load at session start can disappear without anyone noticing. Those procedure files sit under a hard size budget, and past that threshold the tail is silently cut off. A procedure that stops being read still looks fine from the outside. So how the files are loaded is part of the memory design, not just plumbing.

Coordination is not a pointer to a live process

Agents first coordinated by passing messages. That lost work every single time an owner exited: the message arrived for a process that was gone, and the task sat marked as owned forever, invisible to every other agent.

Coordination moved to committed state, and a claim on a work item became a lease (a time-bounded claim re-checked on every read). A dead claimer's item reverts to unowned rather than appearing owned. The general rule, which has since applied well outside this system: coordination state must be durable and re-derivable, never a pointer to something that can exit.

Holding now

An absent process proves the process is gone. "Nobody is holding this right now" is a live-state question.

Responsible for

It never proves the work item has no owner. "Nobody is responsible for this" is a durable-state question, and needs a separate answer.

Isolation followed the same path. A shared working tree let concurrent agents corrupt each other's staged work in ways that only reproduced under specific interleavings, which made them maddening to diagnose. Every session now gets its own isolated tree and index.

Work with no owner

A fleet can produce findings faster than it assigns owners, and ownerless findings are the least likely to survive. Saying one in a session reaches no queue. Writing it into a commit message makes it durable and still unswept: a commit body is a grave. Handing it to another session inherits the pointer problem from the section above, because that session can exit.

So an ownerless finding is filed rather than sent. It goes into a committed queue where it escalates on a schedule of its own, where a claim on it is a lease rather than an assignment, and where it appears in every session's startup summary until it is closed with evidence. The rule that goes with the queue is the part that actually changed behavior: a finding named in a turn and not closed in that turn is filed before that turn ends. The test of whether something was routed is not whether it was written down. It is whether it gets louder by itself.

Measured 2026-08-23, over the 27 days since the queue opened: 2,272 entries filed, 1,104 closed, 1,168 open. Arrivals run about 84 a day against closures of about 41. A typical open entry has been waiting about thirteen days.

Filing forces the question that closing depends on. Every entry has to record how anyone would know it was done. Of the open entries, 42% carry a predicate a machine can evaluate, and 57% carry a written statement of why no predicate can decide it. Nine of 1,168 carry neither. The second category turned out to be the valuable one: "this needs a human judgement, and here is exactly which judgement" is a real answer, and it only exists because leaving the field blank was not allowed.

A duty stated as a level, in a system that produces a flow

The role that owns sweeping the queue had its duty written as dispatching an owner for every unclaimed entry. At the measured arrival rate that is roughly 84 dispatched sessions a day, which nobody can do. The duty had in fact already been rewritten as a rate target, close at least as many as arrive, but the superseded stricter wording was the one sitting in the file every session loads at startup. So every holder of that role auto-loaded, at session start, a duty that could only be failed.

Two consecutive holders then failed identically, and the days-unmet counter advanced straight across the handover. The second holder had taken the role because the first was failing. Replacing the person was the wrong experiment run twice.

When a rule is written in two places, the copy that reaches readers governs, whichever copy is current.

The backlog number was not a count of findings. The queue's own listing runs each entry's closure check under a total time budget, and labels the entries it does not reach as unmeasured rather than dropping them, which is the honest thing to do. But unmeasured was what every session saw. Run to completion on 2026-08-08 instead of under the budget, twenty-two entries turned out to be already resolved and invisible to the entire fleet, still aging, still escalating, and still inflating the count the duty was being graded against. An instrument with a cost bound reports the bound. This is the same distinction the effectiveness instrument makes when it declines to score an under-sampled class, and it is the distinction the next section is about: naming the abstention correctly is necessary and it is not sufficient, because the label is the thing people act on.

Checks that pass for the wrong reason

Everything above is a special case of one thing, and this section is the general form of it. A worked example first, included because the failure is more instructive than the success.

A verifier was checking whether a set of external records was still live. It reported one as live. It was live, but the check had not established that: the network fetch had timed out, the output file was never cleared between calls, and the assertion had matched against the previous request's leftover bytes. Right answer, no measurement.

The correction was to clear state per call, treat a non-zero exit as no verdict rather than as a negative, and then re-run the whole thing against a deliberately fabricated identifier to confirm the check could still tell the difference. That last step is the one usually skipped.

A check never observed to fail has not been shown to work. A passing test tells you the assertion held, not that it held for the reason you believe. The companion rule, from repeatedly being wrong in the other direction: when something fails on model output, the verifier is the suspect before the model is.

An instrument has to name the mechanism, not the symptom.

The sharper version, which took longest to learn: when one observable has two possible causes with opposite remedies, testing the property they share will confidently prescribe the wrong fix for whichever half you cannot see. A burst rate-limit and an exhausted budget look identical at the call site and want opposite responses. So does a bug in the code around the model and a change in the model itself.

The working copy is not the repository

Two more instances of the same disease arrived after this page first published, and both are about a check reading the wrong subject rather than reading it wrongly.

Sessions here run in separate checkouts, most of them partial. A test that asks the local directory whether a file exists is answering a question about one machine and reporting it as a fact about the shared record. The file can be absent locally and present on the branch; a checkout only advances when somebody rebases it, so the local answer can be hours stale while the shared reference is seconds fresh. The correction is to read the shared reference, and to return three states instead of two: present, absent, and could-not-determine. Folding the third into the second is the same vacuity failure in different clothes, and it fails in the reassuring direction.

Landed is not running

A rule can be authored, committed, confirmed present on the shared branch, and pass its own closure check while the old code goes on executing, because the hooks that enforce it, the small programs the version-control system runs automatically at each commit, load out of a different copy of the repository than the one that authored the change. Nothing reports this. It is silent, and it fails in the direction that looks correct, which is the combination that lets a control quietly become documentation. The system now carries a check whose only job is to say, at commit time, that the bytes being committed are not the bytes that will run.

A rule is not delivered until you can name the surface that carries it, say which sessions that surface reaches, and show one instance of it firing or being read.

Context as a deliberately managed resource

Context is the budget everything else spends. Four rules govern it here.

  1. Progressive disclosure

    Of 72 program skills, none load at session start. Each carries a description whose only job is to answer "does this apply to what I am about to do," and the body loads on invocation.

  2. Offload by size

    Any result above a fixed threshold goes to disk with a digest returned in its place, and a cost estimator is consulted before a large read rather than after.

  3. Instrument the trajectory

    Occupancy and remaining context budget (headroom) are queryable mid-task against an explicit rubric for when to checkpoint.

  4. Compact by rotation, not by truncation

    The durable memory index runs against a hard load limit, past which the tail is silently dropped. Roughly 81 percent of the space is pointer scaffolding rather than content, so the tempting lever is shortening each entry's retrieval hook. That is the wrong lever: a hook that no longer says when the entry applies is dead weight still paying its full pointer cost. Rotation is the right one. The first pass took the index from 130 entries at 16.7 KB to 85 fully-hooked entries at 15.6 KB. Today it carries 115 pointers in 20.8 KB against a 24.4 KB limit, with the rest of a 1,446-entry corpus in an archive that stays searchable and restorable.

Three habits fall out of it, and they are the part most likely to transfer to a system that looks nothing like this one:

  • Build an instrument that can disprove a control's effectiveness, then redesign what the evidence rejects.
  • Keep "could not determine" as its own answer. Folding it into "no" is this same failure again, and it lands in the reassuring direction every time.
  • A control is not delivered until you can name the surface that carries it and show one instance of it firing or being read.

The counter-example belongs here too, because the page would flatter itself without it. Not all ten were caught by an instrument. Several were caught by a person reading output and noticing it was wrong; the instrument came afterwards. What the instrument buys is not the first catch. It is that the same failure does not have to be found by luck a second time.

Scope and limits

The evidence is strongest when its boundary is visible. This is where the operating layer sits today.

  • Current access. The layer runs every day for one research program, and a product is being built on it. There is no trial, pricing, or release date yet. The available routes are below.
  • Validation boundary. The load comes from one operator's fleet. No outside team relies on its uptime, and it has not yet been tested against a second operating environment.
  • System category. This is agent orchestration, shared-state integrity, and control evaluation. It does not build or train an AI model.
  • Security boundary. Session isolation protects correctness between cooperating agents. It is not a hostile-code sandbox or a security product.
  • Measurement boundary. These observations describe this system's controls, not agent behavior in general. Every observation span is stated so the evidence can be discounted appropriately.

What it is: the operating layer described above, in daily use since March 2026, measured continuously, and the subject of thirty USPTO applications across twenty families, thirteen of them filed since this page was first published. The surrounding research program is eight papers on SSRN, one published at Frontiers in Blockchain, and fifteen federal regulatory comment letters. The product starts from the distinction this page measures: a configured safeguard is not yet an effective control, and the difference has to be observed.
