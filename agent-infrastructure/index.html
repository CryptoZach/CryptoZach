Agent Infrastructure

Run many AI agents on one codebase while keeping the work coordinated, attributable, and reproducible.

We built an operating layer that isolates concurrent work, records which agent and session produced each shared result and what it relied on, keeps shared references valid, and measures whether safeguards change behavior. It has run on our own fleet since March 2026.

The evidence is below: dated measurements from more than 26,000 commits, the controls that held, the warnings that repeated, and the failures that changed the design.

Why this layer matters

When many agents share a codebase, small errors stop being local. They become shared state that later agents can trust, repeat, and extend. Three requirements keep those errors from compounding.

  • Concurrent work needs isolation. Without separate workspaces and durable ownership, two agents can change the same files and one can quietly erase the other's work.
  • Shared results need identity and provenance. Later sessions need to know which agent produced a result, what evidence and prior state it used, and whether its references resolve to real records.
  • Safeguards need outcome measurement. A warning count shows that a message appeared, not that behavior changed. A gate count shows that it fired, not that it held or was bypassed.

A safeguard you have not measured is a safeguard you are only assuming you have.

The sections that follow show how the operating layer addresses these requirements, what the measurements changed, and where the evidence remains limited to one fleet.

The operating layer

The layer has three jobs. Each replaces something an agent would otherwise have to remember with durable state, a machine check, or a measured outcome.

Keep concurrent work isolated and recoverable

Each session works in its own tree and index. Ownership is stored as a time-limited lease. If a session exits, the lease expires and its work returns to the queue instead of remaining silently claimed. See why process-based ownership failed.

Preserve identity, provenance, and valid references

Shared work records which agent and session produced it, what evidence and prior state it used, and the exact commit that wrote it into the durable record, so any result can be traced to the change that saved it. Findings, decisions, and open questions must resolve to existing records; missing references are surfaced instead of invented. See how an invented reference spread.

Measure safeguards by outcomes

Warnings are graded by whether they return after first appearing. Hard gates are graded by how often they stop an action or are bypassed. That separates controls that teach, controls that enforce, and controls that only appear active. See the measurement method.

Current validation boundary: every number on this page comes from one operator's fleet. The system is operational, but its transfer to a second fleet has not yet been measured. See the full scope and limits.

Measure whether safeguards change behavior

A warning can fire thousands of times and still have no effect. To separate activity from effectiveness, we track what happens after a workspace first sees each warning. A workspace is one agent's isolated checkout of the shared codebase.

The core metric is repeat rate (called saturation inside the instrument): the share of workspaces where the same warning appears again after its first appearance. A high rate means the warning alone was not reliably preventing the behavior. A lower rate may indicate teaching, but it does not prove that the warning caused the change.

The largest result

The warning for treating a failed command as successful generated 8,661 events, more than half of all warnings, and returned in 85% of workspaces. A trigger dashboard would make it look heavily used. Outcome data showed that it was not a reliable control by itself.

This result changed the architecture. Teaching controls now explain the safer action, while enforcing controls stop an action when the wrong behavior can be identified precisely. Each is measured separately.

The result persisted when the observation window was held constant. Over equal 21-day windows either side of 2026-08-04, the failed-command warning moved from 81% to 86%, while the unscoped-absence warning moved from 64% to 48%. The span is stated because the comparison is not reproducible without it: the instrument bounds both windows to the shorter side, so the same command run a week from now compares longer spans and returns different numbers. Six other classes had too few observations to grade, so the instrument returned no verdict instead of a flattering number.

Count what agents do after a safeguard fires, not how often the safeguard appears.

From advice to enforcement

Not every rule should block work. The system uses two levels based on whether the safer action can be identified precisely enough to enforce without stopping valid work.

Teaching control

Explains the safer action but depends on the agent remembering and following it. Examples include a session-start rule, a memory entry, or a warning. It remains guidance until outcome data shows that behavior changed.

Enforcing control

Changes what the agent can do at the moment of action. A gate can refuse a commit or command, while a helper can return the safe form directly. It does not depend on recall, but it must distinguish unsafe actions from valid ones.

A rule is not enforced merely because it is documented, loaded, or triggered. It becomes enforcing only when its delivery path reaches the action and the unsafe choice is refused or removed.

Two design rules follow:

  • Escalate only when the harm and the target are clear. A warning's high repeat rate does not justify a hard gate unless the system can identify the wrong action precisely.
  • Measure false positives and overrides before arming. A gate that blocks valid work will train agents to bypass it or will be disabled entirely.

The strongest control removes the unsafe choice and gives the agent the safe action. When that is not possible, a gate should refuse narrowly and log every override.

The override log is essential. Without it, we could count how often a gate fired but could not tell whether the block held.

An override remains necessary because a gate that blocks valid work needs a recovery path. The same override data also reveals gates that agents routinely step around.

Only 2% of warnings reached a hard gate. A gate is safe to arm only when the wrong action is unambiguous. Destroying a stash or force-deleting a branch can be recognized from the command. Piping one command into another is usually valid, so only a narrow subset of failed-command warnings can be blocked safely.

A precise gate can still reach too little behavior to matter. The narrow failed-command gate has been reached eleven times against 8,661 warnings in the broader class: it refused six and was bypassed five, and every one of the five bypasses came from the same command. Blocks and overrides are separate outcomes here, exactly as in the totals above, so no block was itself overridden. It avoided false alarms but reached about one eighth of one percent of the behavior it was meant to address.

A gate is effective only if it reaches the behavior and agents do not immediately bypass it.

When a gate measures machine load instead of risk

One launch gate blocks new work when it cannot read the current ownership state. A week after arming, that read failed in 22% of attempts, causing dozens of blocked launches each day. Agents used the override in 29% of those cases.

The cause was not conflicting work. The ownership read timed out more often when the machine was busy, so the gate was converting system load into blocked launches. Because a retry often succeeded, the gate trained agents to retry instead of investigate.

With no change to the gate, the same measurement later fell to 1.8%: ten failed reads across 543 attempts, five blocked launches, and no overrides. The control did not improve. Machine load fell.

Measure what drives a gate's trigger rate, then count how often it fires.

Shared memory needs identity and provenance

Memory capacity and retrieval matter only after the record can be trusted. Before one agent reuses another's result, it needs four answers: does the referenced fact exist, which agent and session produced the result, what evidence and prior state did it use, and which commit wrote it into the durable record?

The failure that forced this design was not forgetting. An agent confidently cited a finding that had never been established. The next session accepted the citation as real and built more work on top of it. This is confabulation: a made-up fact stated as true. In shared memory, one invented identifier can become load-bearing within a few sessions.

  1. Require valid references when work is saved

    An agent may not invent an identifier for a finding, decision, or open question. If the record does not exist, the reference remains empty and is flagged for human review.

  2. Preserve attribution with the result

    Shared work records the producing agent and session, the evidence and prior state it relied on, and the committed change that placed it in the durable record.

  3. Verify that instructions reached the reader

    Startup procedure files have a hard size limit. Content beyond that limit can be silently omitted, so loading and size are memory-correctness requirements.

Shared memory is trustworthy only when records are valid, attributable, and known to have reached the reader.

Coordination must survive the agent

A task is not durably owned merely because a running process received a message. The early system coordinated that way. When the receiving agent exited, its task could remain marked as claimed even though no one was working on it, leaving the rest of the fleet unable to see or recover the work.

Now every claim is stored in committed state as a lease: a time-limited ownership record checked whenever the queue is read. If the lease expires or its holder is gone, the work returns to the available pool instead of remaining silently owned.

Who is working on it now?

This is a live-state question. An absent process can show that the current holder is gone.

Who remains responsible?

This is a durable-state question. A stopped process does not erase the work item's history, responsibility, or next action.

Leases protect ownership state; isolated workspaces protect the files. Every session receives its own working tree and staging index, so one agent cannot silently alter another agent's pending commit.

Coordination state should outlive the process that created it.

Ownerless work needs a queue that escalates

A finding mentioned in a session can disappear when that session ends. A finding written only in a commit message is durable but has no process that will return to it. Sending it to another live agent creates the same dependency on a process that can exit.

The system therefore files ownerless findings in a committed queue. Each entry appears in every session's startup summary, escalates as it ages, and can be claimed only through a time-limited lease. It leaves the queue only when it closes with evidence.

Every entry must say how closure can be verified. Of the open entries, 41% state a condition a machine can evaluate, and nearly all of the rest explain the specific human judgment required. Eight entries have neither. Requiring an answer turns “needs human review” from a vague deferral into a named decision.

A flow cannot be managed as an absolute backlog

The queue owner was originally told to assign every unclaimed entry. At 81 arrivals a day, that would require roughly 81 new assignments every day. The workable duty is a rate target: close at least as many entries as arrive.

The obsolete absolute duty remained in a startup file after the rate target replaced it. Two consecutive role holders then failed in the same way because both loaded the same impossible instruction. Replacing the person did not change the rule they received.

When a rule is written in two places, the copy that reaches readers governs, whichever copy is current.

A bounded scan reported its budget, not the backlog

The queue listing checks whether entries are already resolved, but it stops after a total time limit. Entries it does not reach are labeled unmeasured. A complete run on 2026-08-08 found 22 entries that were already resolved but still aging, escalating, and inflating the visible backlog.

The label was honest, but it was still the number every session acted on. When an instrument stops early, readers need both the measured result and the size of the unmeasured remainder.

A passing check can still be wrong

A green result shows that an assertion matched. It does not show that the check measured the intended subject, used fresh state, or could distinguish a true case from a false one.

Right answer, invalid check

A verifier reported that an external record was live. The record was live, but the network request had timed out and the assertion matched bytes left behind by the previous request. The answer was correct by accident.

The correction was to clear state before every request, treat a failed request as could not determine, and test a deliberately false identifier to prove that the verifier could reject it.

A check never observed to fail has not been shown to work.

Different causes can share one symptom

A burst rate limit and an exhausted usage budget can produce the same error while requiring opposite responses. A defect in code around a model can look like a model failure. The check must identify the mechanism, not merely recognize the shared symptom. When model output appears wrong, the verifier is tested before the model is blamed.

The local checkout is not the repository

Each session runs in a separate, often partial checkout. A missing local file means only that the file is not present in that checkout. The shared branch may already contain it, and the local copy may be hours behind. Repository-state checks therefore read the shared reference or staged index and return three answers: present, absent, or could not determine.

Committed is not running

A rule can be committed to the shared branch while an older copy continues to execute. This happened when commit hooks loaded their code from a different checkout than the one carrying the new rule. The system now compares the bytes being committed with the bytes the hook will actually run.

A rule is delivered only when you can name how it reaches agents and show it being read or enforced.

Context is a finite operating budget

An agent's context window limits what it can actively consider. Loading every procedure, source, and prior result at startup can crowd out the evidence needed for the current task. Four rules keep that budget usable.

  1. Load procedures only when they are relevant

    The system has 72 program skills, but none loads automatically at session start. Each skill exposes a short description first; its full instructions load only when the task requires them.

  2. Write large results to durable storage

    Results above a fixed size go to disk, while the agent receives a short digest and a path. A cost estimator checks large reads before they consume the context window.

  3. Measure remaining context during the task

    The agent can query occupancy and headroom, meaning the context still available. Explicit thresholds say when to continue, checkpoint the work, or hand it to a fresh session.

  4. Rotate memory instead of weakening retrieval

    The startup memory index has a 24.4 KB load limit, and 81% of its lines are entry pointers rather than structure. Shortening the text that says when an entry applies would make retrieval less reliable, and trimming the other 19% reclaims almost nothing, so entry count is the only real lever. The system therefore rotates complete entries into a searchable archive. The live index now carries 105 fully described pointers in 19.7 KB, while the rest of the 1,466-entry corpus remains searchable and restorable.

Context management should preserve retrieval quality, not merely reduce bytes.

Ten failures, one pattern: the signal looked healthy

Each failure here was quiet: nothing crashed and no error appeared. A warning fired, a claim was held, a check passed, a rule was committed, and each of those signals looked like a control doing its job. In every row, a second measurement showed the signal meant something else.

The most dangerous control is one that fails silently toward the reassuring answer.

Three practices transfer beyond this system:

  • Test a known false case. A check that has never rejected anything has not shown that it can distinguish success from failure.
  • Keep “could not determine” as its own result. Folding uncertainty into absence produces a reassuring answer the evidence does not support.
  • Verify delivery and execution separately. Show both how the control reaches agents and which version is actually running.

Measurement did not discover all ten failures. People found several by noticing that the output did not make sense. The value of the instrument is turning that first discovery into a permanent check, so the same failure does not depend on luck a second time.

What this evidence does and does not establish

The operating layer is real, measured, and used daily. It is not yet evidence of reliability across different organizations or workloads. The boundaries below keep those claims separate.

  • Current access. The layer runs every day for one research program, and a product is being built from it. There is no public trial, pricing, or release date yet. The available ways to engage are below.
  • External validation. Every measurement comes from one operator's fleet. No outside team depends on its uptime, and transfer to a second operating environment has not yet been measured.
  • Technical scope. The layer coordinates agents, preserves attribution and shared-state integrity, and evaluates controls. It does not build or train an AI model.
  • Security scope. Isolated sessions protect cooperating agents from corrupting one another's work. They are not a sandbox for hostile code or a substitute for a security product.
  • Generalization. The results describe this system's controls, not AI-agent behavior in general. Observation periods and counting rules remain attached so readers can judge how far each result should travel.

What exists today. The layer has run on our fleet since March 2026 and is measured continuously. Its architecture is covered by thirty USPTO applications across twenty families. The surrounding research program includes eight papers on SSRN, one peer-reviewed publication in Frontiers in Blockchain, and eighteen federal regulatory comment letters.

The product thesis. A configured safeguard is not yet an effective control. The difference becomes visible only when the system measures what agents do after the safeguard fires.
